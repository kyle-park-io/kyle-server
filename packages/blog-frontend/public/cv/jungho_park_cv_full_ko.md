### **matching-ledger**: 거래소 매칭 엔진과 정산 원장

_기술 스택: Rust_

- **재생 일치와 장애 복구**: 거래소 매칭 엔진의 정합성과 장애 복구를 위해, 주문을 입력 로그에 순서대로 적고 스레드 하나가 그 순서대로 체결해 언제 다시 돌려도 같은 체결이 나오는 single-writer 매칭 엔진을 Rust로 구현. 합성 주문 로그 10개를 조건 16가지로 320번 재생해 매번 같은 상태가 나왔고, 2만 건이 든 로그 하나의 끝을 2,000곳에서 자르거나 깨뜨려도 손상 앞까지 온전히 복구했으며, 로그만 쓰는 프로세스를 100번, 엔진 프로세스를 300번 강제 종료해도 응답한 주문을 잃은 경우가 0건. 2026년 11월 데스크탑에서 잰 값

### **judgment-pipeline**: 기사 판정 메시지 파이프라인과 브로커 4종의 장애 시험

- **소비자 장애와 멱등 처리**: 메시지 소비자가 처리 도중 죽어도 기사 판정이 유실이나 중복 없이 한 번만 반영되는지 확인하려고, 브로커마다 소비자를 86번 강제 종료하는 장애 주입 시험을 돌림. 처리를 마친 뒤 ack하는 방식은 Redis Streams, NATS JetStream, Kafka 모두 유실 0건이었고, 기사 ID를 기본 키로 둔 결과 테이블은 행 수가 보낸 46,192건, 46,212건, 149,229건과 같아 중복 0건. 같은 시험에서 기본 키를 뺀 테이블에는 Redis Streams, NATS JetStream, Kafka 세 브로커 모두 같은 기사가 두 번 반영돼, 중복을 막은 것이 기본 키임을 확인. 브로커를 고를 기준으로 장애를 넣지 않은 평상시 지연도 재서, 메시지 하나의 지연 p50은 32번 반복의 중앙값으로 Redis 1.94ms, NATS 2.10ms, Kafka 2.24ms. 2026년 11월 데스크탑 WSL2에서 장애 시험은 50ms 걸리는 가짜 판정기로, 지연 시험은 지연 없는 가짜 판정기로 잰 값
- **transactional outbox와 브로커 영속 설정**: DB 트랜잭션과 메시지 발행은 따로 실패할 수 있어, 그 사이에 생산자가 죽어도 데이터 일관성이 깨지지 않는 방식을 찾으려고 브로커마다 3,000행 넘게 쓰는 동안 생산자를 40번 강제 종료함. DB 커밋 뒤에 발행하면, 생산자를 브로커마다 40번 강제 종료했을 때 DB에는 들어갔지만 메시지가 나가지 않아 결과가 생기지 않은 원본 행이 브로커에 따라 33에서 38개, 발행 뒤에 커밋하면 원본 없이 결과에만 생긴 행이 1에서 11개였고, 원본 행과 보낼 메시지를 한 트랜잭션에 쓰고 릴레이가 발행하는 transactional outbox는 생산자와 릴레이를 합쳐 40번 강제 종료해도 Kafka, Redis Streams, NATS JetStream, RabbitMQ 모두 어긋난 행이 0건. 브로커가 재시작돼도 수신을 확인한 메시지가 남는지 설정마다 견주니, 브로커 컨테이너를 강제로 끄고 다시 띄우는 시험을 세 번씩 돌리자 Redis 기본 설정, NATS 메모리 저장, RabbitMQ 비영속 메시지는 종료 전에 확인한 메시지를 모두 잃었고 Redis AOF, NATS 파일 저장, Kafka, RabbitMQ 영속 메시지는 세 번 모두 하나도 잃지 않음. 2026년 11월에 잰 값

### **크로논랩스 기능 재현 시험**: 퇴사 뒤 크로논랩스에서 만든 기능을 다시 구현하고 다른 구조, 프롬프트, 연결 방식과 같은 조건에서 견준 개인 시험

_기술 스택: Go, Rust, Python_

- **Solscan 호출 조정기**: Solana 봇의 홀더 분석 서비스 여러 개가 외부 API인 Solscan의 호출 한도 하나를 나눠 쓰므로, 한도를 넘지 않으면서 급한 호출을 먼저 보내는 구조를 견줌. 크로논랩스에서 쓰던 서비스마다 동시 2건과 호출 뒤 200ms 대기 대신 우선순위 채널과 토큰 버킷으로 호출 간격을 고르게 두자, 합성 호출 10,000건을 세 번 돌린 중앙값으로 한도 초과 응답이 155건에서 0건, 급한 호출의 대기 p99가 238ms에서 111ms로 줄었고, 간격을 고르게 둔 만큼 급한 호출의 대기 p50은 0.007ms에서 35.6ms로 늘어남. 생산자와 소비자 여럿이 ID 100만 개를 넣고 꺼내는 스트레스 시험 72번에서 크로논랩스의 링 버퍼를 다시 만든 구현은 매번 ID를 잃었고, 칸마다 순서 번호를 둔 링 버퍼는 한 건도 잃지 않음. 2026년 11월에 Go로 다시 구현해 분당 1,000건 한도의 모의 서버에서 세마포어, 링 버퍼, 우선순위 채널, 단일 채널, 칸마다 순서 번호를 둔 링 버퍼의 다섯 구조를 견줌
- **뉴스 판정 LLM 평가 하네스**: 크로논랩스에서 실주문에 연결했던 LLM 뉴스 판정을 다시 구현하고, 판정이 기사 ID를 바꾸거나 순서를 밀지 않는지와 같은 기사의 점수가 얼마나 흔들리는지 재는 평가 하네스를 만듦. strict JSON 스키마로 부른 판정은 비교 기사 30건을 넣은 조건에서 고치기 전 프롬프트와, 기사를 JSON으로 넣고 기사 ID를 식별자로만 쓰라는 지시를 더한 프롬프트를 75번씩 불러 기사 ID와 순서가 한 번도 어긋나지 않았고, 고친 프롬프트에서는 같은 기사를 5번 판정한 점수(0에서 100점)의 표준편차 평균이 2.92에서 1.73으로 줄어듦. 2026년 11월에 gpt-4.1 Batch API로 잰 값
- **상장 공지 수신 지연**: 상장 공지를 더 빨리 수신하려고 요청 지연을 DNS, TCP, TLS, 서버 응답 구간으로 나눠 재는 측정기를 만들고 지연이 어디서 생기는지 찾음. 연결을 재사용하면 요청 지연 p99가 새 연결의 62.0ms에서 재사용 세 방식의 18.8ms, 20.9ms, 21.5ms로 40ms 넘게 줄지만, 1초 폴링 대기를 더한 모형에서 공지를 알아채기까지의 지연은 어느 방식이든 p99 1,001에서 1,023ms라 지연 대부분이 폴링 주기에서 나온다는 것을 확인. 2026년 11월에 공지 경로 대신 Upbit 페어 목록 조회 API를 초당 한 번씩 6,000번 불러 새 연결 방식과 재사용 세 방식을 견준 값
- **Delta 청산 정책 재생 시험**: Binance, Bybit, MEXC에서 기록한 호가를 재생하는 시험을 만들고, 크로논랩스가 남은 Delta를 잔고가 가장 많은 거래소 한 곳에서 청산하던 정책을 다른 정책 5가지와 같은 호가에서 견줌. 여러 거래소로 나눠 청산하면 건당 총비용이 6.8bps 낮았고 95% 신뢰구간은 6.1에서 7.5bps였으며, 거래소마다 자기 중간가로 슬리피지를 재도 5.5bps 낮았음. 2026년 11월에 자산 8개의 호가를 24시간 기록해 무작위로 뽑은 모의 청산 29,773건마다 정책 6가지를 모두 적용한 값이며, 크로논랩스 자동 밸런서의 이체 규칙을 다시 구현한 모형과 모의 잔고, 가정한 수수료와 위험 비용 아래의 값
